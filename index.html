How it works

A GitHub App that gets smarter with every PR.

01

PR opened → webhook fires

GitHub sends a pull_request event. Govux verifies the HMAC signature and enqueues a governance job.

→
02

AST pipeline runs

Two-pass Babel + TSC analysis builds a ComponentUsageMap — props, ARIA attributes, import sources, and type-resolved signatures.

→
03

Agents analyse + score

Five governance agents run in parallel. LLM pass (optional) adds semantic checks against design-system specs. Violations are diff-baselined: new vs. pre-existing.

→
04

Results posted back

GitHub Check Run passes or fails. Inline review comments pinpoint exact lines. Every 10th analysis the Spec Memory System runs and updates org-specific amendments.

Model Context Protocol

Governance inside every AI coding session

The Govux MCP server exposes 6 tools to Cursor, GitHub Copilot, and Claude Desktop. AI agents query your org's governance state before writing code — not after a PR is opened.

  • get_design_system_policy — scoring weights & enforcement mode
  • get_component_inventory — components with risk signals
  • get_accessibility_policy — WCAG rules + org overlays
  • get_violation_history — recurring violation patterns
  • check_component — real-time JSX snippet check
  • get_spec_amendments — org-learned suppressions

💡

AI agents in your org share the same calibrated governance knowledge — no per-developer configuration.

Available MCP tools — what the AI agent sees before writing code
get_component_inventory Before choosing a component Knows which components have recurring a11y issues, deprecated props, or hardcoded string patterns in your specific codebase — picks the right one first time.
get_violation_history Before writing JSX Sees the top recurring violations for your org (normalised via canonical_id amendments) — avoids repeating patterns the team is actively trying to fix.
check_component After writing a snippet Real-time governance check against your org's rules. With do_not_flag amendments wired in, only flags real issues — not historical false positives.
get_accessibility_policy When implementing interactive UI Returns your org's WCAG baseline plus any custom a11y overlays — AI agent writes accessible code to your specific standards, not generic WCAG alone.
get_design_system_policy Before any component work Scoring weights, enforcement mode, scan config — agent understands what your org values most and prioritises accordingly.
get_spec_amendments Context loading Exposes all approved suppressions, canonical IDs, and escalations — agent can reason about what your org has learned and calibrate its output.

The LLM finally has memory.

The Spec Memory System analyses historical patterns and generates org-specific prompt amendments.

Signal 1

Canonical IDs

Same violation gets different ruleId strings across PRs. Picks the most-frequent ID and normalises all history. Auto-approved

Signal 2

Do Not Flag

LLM rule fires exclusively on pre-existing code across 3+ PRs. Suppresses it from future prompts. Auto-approved at high confidence

Signal 3

Skip AST Overlap

LLM duplicates what the AST already found on the same component across 3+ PRs. Removes the duplicate. Auto-approved

Signal 4

Escalate

Real violation recurs as new across 4+ PRs without being fixed. Surfaced for human review in the dashboard. Human review
